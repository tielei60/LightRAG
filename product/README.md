准备器按原文条款结构组织完整责任，保留父级前提、同文件明确引用的定义及完整计划表。正文主区间完整覆盖原始解析文字；附入引用单独登记位置和摘要。v2最大片段3521 token，v3最大片段3527 token，v5最大片段2441 token，超出完整单元上限会停止，不能静默截断。已核对两份条款物理第2页；完整PDF解析质量与业务范围仍需核对原件。

抽取模型仅选择证据编号，程序逐字复制对应原文。全部片段通过协议、编号、身份、名称及启用的表格/范围语义校验后，持久化核准结果，再通过官方 `ainsert` 回放写入原生文档、片段、图和向量，写入阶段不再次随机抽取。合法编号不等于语义正确；来源角色副本目前仍可能重复抽取，需观察合并描述及检索噪声。

证据台账按来源版本和原文位置去重，绑定模型、提示、清单与原文摘要；缓存恢复限定到已激活来源。导入完成关闭写进程，再读回原生文件和三类向量；最后启动原生服务。不要在 SDK 导入时启动同工作区的服务，也不要从普通上传入口重传本批资料。

## 当前问答方式

沿用原生 `mix` 检索、关键词与阿里云重排；使用公开的 `WEIGHT` 选择已命中图实体的来源片段，实体/关系预算2000/2500，总预算18000，片段上限12。模型的事实依据为同次检索到的完整原文及真实标题、上级条件和定义。图描述只用于定位，不替代原文支持的判断。

默认入口为 `product.server` 的 `AnswerQuery`。它将所有候选原文按实际文件引用归组，模型可见的引用只有文件编号；内部片段编号仅用于追踪。实际配置的 `USER_PROMPT_PREFIX_FILE` 作为可信问答指令生效。`qwen3.7-plus` 一次调用直接生成答案，真实模型文本流逐段返回；不调用旧 `GroundedQuery` 的证据选择、补证、标题过滤或原文渲染流程。旧模块留作历史诊断及来源解析复用。

原生旧答案缓存和自然回答缓存均关闭，避免旧摘录被当作生成结果复用。模型引用未知文件、流异常或超时会显式报错；程序不猜测引用映射，不回退原文展示。引用句法校验只能证明编号来自本次资料，语义准确性仍按每次真实回答及原文独立核查。

## 抽取配置的扩展

评估结论：保留“模型选择证据编号、程序复制原文、使用原生实体/关系协议”的方向；扩展的重点是**产品身份与适用范围、规则分支完整性、资料之间的引用依据**，随后才是增加类型。仅扩大词表不能解决款别串用、销售方与承保方混淆、年度规则覆盖或组合产品缺证问题。

本次对照 `docs/insurance_docs/` 的实际资料和当前 `product/` 实现评估。2026-11-11 整理后，知识资料目录保留49个产品目录、140份资料（105 PDF、12 Markdown、20 DOCX、3 DOC），另有1份官网抓取清单；89份费率/现金价值表（46 PDF、43 XLSX）已移至同级 [`docs/insurance_calculation_tables/`](../docs/insurance_calculation_tables/)，保留48个产品子目录及原文件名。目录数不等于独立合同产品数。下文列出重点核读的原文及位置，是配置设计依据，不代表全部资料已完成业务审核或已导入。

**范围约定：只排除独立的费率表文件、现金价值表文件；条款及其他知识资料中的现金价值等合同内容正常导入。** “不导入表文件”不等于“不导入现金价值知识”。现金价值定义、退保/合同解除权益、给付或退还条件、公式、比例基数以及现金价值归零等后果均应保留，并可形成“现金价值”实体及“适用现金价值规则”等关系。带有产品归属和原文证据的“现金价值”实体属于正常抽取结果。

独立计算表文件已物理分离，[迁移清单](../docs/insurance_calculation_tables/迁移清单.json)保存原路径、新路径、大小及 SHA256；官网抓取清单的本地文件路径已同步更新，来源 URL 与原摘要保留。准备器默认只读 `docs/insurance_docs/`，不会扫描同级 `docs/insurance_calculation_tables/`；既有批次的历史清单不回写。排除按独立文件用途识别，与文件格式无关，不能按正文出现“现金价值”“费率”或金额、公式来删段落、表格、片段或实体。条款和说明书中的相关规则及必要表格随完整原文、适用条件和脚注保留，计划—责任对照表、疾病定义表和药品目录也正常导入。精确金额查算由其他系统负责，利益演示值不能作为标准报价或保证收益；不提供金额计算不影响相关合同知识入库。

| 产品前缀、计划/责任范围、组织不加产品前缀 | 有助于防止同名责任跨产品合并；计划/渠道/年份范围的正确选择目前主要依赖提示，尚无完整的适用范围校验 |

| 自动资料发现 | `prepare_batch.discover()` 要求恰好一份条款 PDF、一份说明书 PDF、一份投核保 Markdown；对当前49个目录做只读发现检查，仅9个通过这一形状要求，**不等于9个已可验收** |
| 证据来源与根身份 | `EvidenceChunk` 要求同一来源、同一原文及可在原文核实的产品名；`to_native()` 仅接受该片段已核产品根。不能直接把另一合同产品作为第二个根，也不能把不同文件的编号拼到同一关系中 |

**多款、多渠道、跨年份：都需要抽取，但不使用同一条“版本”关系解决**

| 维度 | 判断及建模建议 | 合并/复用边界 |
| --- | --- | --- |
| 产品系列 / 销售名称 | 用于检索导航；记录销售名称与正式合同产品的有据映射。爱她保2025引用多份具名条款，不能把销售名称直接等同于其中任意一份 | 名称近似、同文件夹或同销售机构都不足以证明同一合同产品 |

| 保障计划 / 责任组合 | 同一产品下分别记录计划一/二和基本/可选责任组合；已购买哪项责任仍由具体保单确定 | 共同责任可以复用，但不同给付金额、前提或后果须有各自范围的规则节点；不能把共同部分推成所有差异规则共用 |

1. **一个产品多款，大部分条款相同。** 先确认“独立合同款别”还是“同合同计划”，再识别共同内容。条款文字相同还须核对引用定义、上级前提、除外责任、适用人群和版本是否一致；一致时可在资料层复用原文及经过核定的适用映射，不等于把A款/B款的业务节点合并。当前实现优先在各自范围保存完整证据，差异节点命名为“产品全称｜明确款别或计划｜责任原称｜规则短名”，仅加入原文明示且未在全称中表达的维度。不要把B款当A款的默认子类，也不要让模型根据相似度自行补齐“其他相同”。跨款共用的系列/条款目录可先在准备清单维护；现有“产品系列”节点也带产品前缀，不能靠把它加入 `unscoped_entity_types` 就视为已解决跨产品身份。

2. **同一产品跨机构、跨渠道销售。** [爱她保2025投保须知][src-aita-notice]第1、4项明确：众惠财产相互保险社是主承方，北京人寿保险股份有限公司是从共方，山东智诚惠民经纪有限公司通过互联网平台在全国销售。因此该资料同时支持共同承保和经纪销售，不能把北京人寿仅记为销售方，也不能把销售公司记为承保方。[服务协议][src-aita-service]另列服务提供方，必须按具体服务建立关系。“北京人寿普惠保”公众号被列为咨询或业务入口，不足以证明存在独立直销合同或另一套直销保障规则；若另有渠道资料，需补齐证据后才建立该渠道的适用联系。组织实体可以共用，机构角色和适用产品/年度/计划须随关系保留。

3. **2025基础版，2026只变更投保年龄。** 这是应支持的增量修订场景，不能先当作本目录已验证事实。需要原文确认基准版本、被修订条目、新年龄边界、生效时间、适用渠道/人群，以及对新投保、续保和既有保单的适用范围。若完整新版及依赖条款比对一致，或有效修订文件明确“仅修改该项，其余沿用”并准确指向基准，才可复用其余规则。保存基准原文、修订原文及映射，在新版本范围替换年龄规则；旧版本仍用于旧合同查询。没有“其他不变”的依据时记录已知差异与未核对项，不能推断未提及的规则均不变。目录中的京康岁悦原版与2026版已有给付结构差异，不能作为“只改年龄”的实例。

增量修订的后续处理顺序应为：**核定基准与修订关系 → 核定生效及适用范围 → 标明规则新增/替换/删除或确认沿用 → 形成该范围内可独立核查的有效规则集合 → 验证引用和问答**。这是一项待实现的资料处理能力，不是要求模型在回答时临时拼接多个版本。显式删除必须记录，不能因为新版没再提到就当作删除；两份来源冲突时保留双方证据并标记待核，不能按“较新文件优先”静默裁决。特别约定或批单也只有在证据证明其对当前合同/范围有效时，才覆盖其明确修改的内容。

**主险与附加险的表达**

主险/附加险是合同关系角色，和同一合同内的基本责任/可选责任不同。产品根统一保留“保险产品”类型；有具名主合同引用时，用“保险合同”实体和“附加于”关系保留角色及依附方向，实体仍使用当前产品前缀。这表示原文允许的合同组合，不表示某人已购买，也不绕过当前只有一个已核产品根的协议。主险自身条款或责任没有提供时，不因存在引用就补全其保障。

- 附加住院医疗意外保险 §1.1 明确指定主合同，可以抽取具名“主合同｜北京人寿住院意外伤害保险合同”引用；期间、终止/中止/无效联动以及 §6.4 的冲突处理作为附加险自己的合同规则保存，不能反向推导“附加险终止，所以主险终止”。
- 附加投保人豁免保险费D款 §1.1 只限定“认可的人身保险合同”，因此先抽取主合同适用范围，不猜主险名称、不向目录中所有主险连边。§1.3 的投被保险人关系、§2.2 的“主合同及指定附加合同”续期保费豁免范围分别留证；“豁免保费”连接豁免责任与被豁免合同范围。附加合同被保险人是被豁免合同投保人，不默认等于主合同被保险人。

两类示例已写入配置并有回归测试。具体主险和附加险产品根之间的跨来源身份关联，仍须后续已核映射支持；当前合同引用节点不能冒充已完成的多产品统一身份。

先收紧类型边界和范围指导，再增加有实际检索收益的少量类型。类型标签只用于分类，给付触发、适用条件和结果仍以完整证据为准，不把每个年龄、百分比、金额都拆成节点。

| 调整项 | 建议及依据 | 落地边界 |
| --- | --- | --- |

| 通用类型与提示长度 | “人物、地点、时间、金额、其他”保留为有依据的兜底，不默认逐项生成；新增11组示例覆盖款别、渠道、修订、缺基准、护理、万能、红利年金、计算表边界及主附险 | 示例当前仍全部发送；后续按固定问题衡量抽取效果和提示开销，再决定是否按险种选取。选择结果须纳入契约摘要，不随机删减 |

款别、渠道和时间范围不能只写进一个松散的“版本”节点。建议在**准备清单/证据台账**保存：核准合同产品身份与销售名称映射、原文明示款别和计划、承保/销售/服务机构及角色、明确的渠道范围、业务版本与生效区间、适用新单/续保/既有合同的条件、基准/修订引用及对应证据、来源摘要与原文位置。每个适用范围判断都要能指回来源；未说明记为未知，不能默认全渠道、全年份或全部计划。上述是未来清单设计要求，**当前 profile 不接受这些新键，也没有对应的自动继承解析器**。

组合产品还须先扩展已核身份与引用的准备契约。例如爱她保投保须知第19项确实引用六份具名条款，但这些条款正文未必出现“爱她保2025”，不能给原文补一个销售名就绕过当前身份检查。应登记“销售组合—适用条款—计划/组合”的可追溯映射，在准备层核实后再组织证据；跨文件关联同时保留引用端和被引用端的来源，缺少基准或附件正文时仅保留引用事实。当前同来源证据目录尚不支持这种联合证明，需先实现并测试，不能只改提示宣称支持。

同样，4—7号爱她保特别约定的正文没有复述文件名中的计划标签。文件名可帮助整理，不能单独证明计划归属；导入前须由配套清单、原始发布关系或业务核定补足映射依据。目录中的多格式副本也应先核来源和内容差异，再选权威表示或保留独立版本，不能按排序随便选一份、也不能重复导入强化同一事实。

**证据单元、检索与回答的配合要求**

- 以能独立说明一个完整业务分支的单元取证，同时带上产品/计划范围、主体、前提、触发事件、时间与年龄边界、比例基数、次数/限额、例外和后续状态。未提供的内容不补齐；“本项责任终止”与“本合同终止”不能互换。
- 同一单元同时有条件和给付结果时，优先一个有完整原文的规则节点；只有确有独立检索价值且关系有直接依据时再拆分。各计划共用同名责任但规则不同，可以连接各自有范围的规则节点，不能把互斥规则拼成一个无范围描述。
- 计划责任表必须携带表名、行列头、单位和脚注；0、空白、破折号和未提供分别保留。独立费率表文件、现金价值表文件不导入，也不为金额查算临时加入检索；条款中的现金价值定义、权益、公式和必要表格正常入库，不按关键词排除。
- 相同原文副本可在明确来源身份内去重，不丢弃不同文件、版本或位置的溯源。共同前提只为相关分支提供支持，不能据此把全部父条款反复抽成新事实或增加证据权重。
- 查询款别、计划、渠道或年份不明确，且答案确有差异时，应追问必要维度或分范围列出，不能默认最新版、最宽松年龄或最多保障。指定旧保单时按其适用版本取证；实际年龄符合条件也不等于个案已通过核保。
- 准确金额查询交由外部计算系统，LightRAG 可以解释条款中的计算依据并引用原文，不能据利益演示、相似产品或模型心算给出正式金额。本次不实现外部计算接口。

这些回答约束需要在候选批次的实际检索上下文中验证。将范围写入节点名和提示只能降低误用，不能代替查询前的身份/版本解析、适用范围筛选和冲突检查；后几项属于待补能力。保持原生图字段不变，仍用 `name/type/description` 和 `source/target/keywords/description`，不向指针输出追加 `scope`、`effective_date`、`relation_type` 等未支持字段。

**配置变更与迁移约束**

新增实体类型时，将规范类型加入 `entity_types`，补充其与近似类型的边界，按需添加确为同义的旧名称别名，并至少增加一组有完整原文证据的示例。新增关系时，注册关键词并写清主体、对象、条件和适用范围；原生图是无向图，方向和动作含义必须由原文描述保留，不能只靠端点顺序。涉及新清单字段、跨文件来源或查询筛选时，需同步修改相应准备/校验实现，不能只往 YAML 添加未知键。

每组证据编号示例都提供 `input.product`、`input.source_file`、带编号的 `input.evidence` 以及 `output.entities` / `output.relationships`。实体与关系只选 `evidence_ids`，描述由程序复制完整原文。示例使用明确的虚构产品名，只演示协议和业务结构，不作为实际产品知识。原生JSON与证据编号示例应表达相同事实，不能把参考配置中的概述描述直接当作原文摘录。

准备目录中的 `primary`、`product-identity`、`structural-parent` 和 `explicit-definition-reference` 角色会传给抽取模型，帮助区分主片段与附入的共同前提/定义；不能把这些证据角色当成条款、核保规则、特别约定或销售资料的文档角色，后者需由资料清单另行说明。

类型、关系、示例或证据角色变化都会影响抽取契约。预览会先验证配置、示例及证据目录，非法类型、未知关系、越界编号或端点缺失会阻断。已有图谱不会因修改配置自动更新；验证新配置应新建候选批次。需要完整重抽时，不使用旧批次的 `--approved-from`，该选项只重新校验旧选择，不会发现新增实体或关系。

原有证据目录中经过核定的类型白名单仍然生效。例如旧批次某些前置内容只支持产品和组织，增加“产品文档”类型不会自动放开这些证据；应核对原文后在新候选中调整证据目录，不能靠修改类型词表绕过来源限制。复用旧选择也不能跳过新版本、渠道和角色的业务复核。

## 操作

在仓库根目录执行：

```sh
make -f product/Makefile status
make -f product/Makefile start
make -f product/Makefile stop
make -f product/Makefile verify
make -f product/Makefile qa
```

默认批次为 `two-products-v5`；管理基线时显式追加 `BATCH=two-products-v2` 或 `BATCH=two-products-v3`，分别使用9621/9622。`start/status/stop` 默认管理9623服务，`verify`只检查已发布的落盘索引，`qa`通过原生HTTP执行11类问题各3次，保存同次回答引用的片段及首字、总耗时。片段引用不是完整模型提示，独立诊断请求也不能冒充历史回答实际上下文。

需要核对某次回答实际使用的完整模型输入时，先停止HTTP服务，再执行 `.venv/bin/python -m product.query_trace --batch two-products-v5 --repeat 1`。该工具通过公开角色回调捕获同次原生SDK问答的系统提示、用户输入和回答；诊断临时关闭原生关键词/回答缓存，保留磁盘缓存，不能将其耗时当成缓存命中速度。结束后重新 `start`。

新批次复现（必须使用新的批次名和工作区）：

```sh
.venv/bin/python -m product.prepare_batch --batch NEW_BATCH --workspace NEW_WORKSPACE --products 京康优护 京安泰
make -f product/Makefile BATCH=NEW_BATCH evidence-preview
make -f product/Makefile BATCH=NEW_BATCH evidence-import
make -f product/Makefile BATCH=NEW_BATCH verify
make -f product/Makefile BATCH=NEW_BATCH start
```

复用v5验证配置时，新批次的 `runtime.env` 还需启用 `PRODUCT_GROUNDED_QUERY=true`，设置 `KG_CHUNK_PICK_METHOD=WEIGHT`、实体2000/关系2500/总计18000，并保留顶部模型与重排设置。导入前将提示复制到该批的 `prompt_profiles/` 并让 `PROMPT_DIR` 指向副本；原文准备命令本身不会冻结这些问答设置。

准备器拒绝覆盖既有批次；导入器拒绝重放已有目标或上传回执。失败后先检查回执、状态与日志，不删除它们盲目重导。准备失败不会创建半成品批次；预抽取失败可在相同配置下恢复已核准台账，原生写入失败则保留目标供检查。

`output/<batch>/` 保存清单、排除项、原文位置图、证据目录、核准输出、模型调用、原生回执、读回及问答报告。技术检查通过不能替代业务验收，重点核对计划责任组合、可选前提、60%比例基数、共享免赔额的适用范围、跨产品同名责任和缺证拒答。

## 结构与效果检查边界

PDF的legacy解析保存展平文字，不提供逐页结构sidecar。与同一解析器输出一致只能证明提取结果已保存，不能证明表格行列、注释和全部图文完整。官方P分块依赖解析sidecar；没有sidecar会退为R，不能仅改一个分块参数就恢复PDF结构。Markdown的原生标题和表格结构也不能自动证明跨条款条件已完整。

检查按“原件→解析→片段→实体关系→实际上下文→原答”定位。先核原文是否读全、条件是否保留及产品归属，再判断应调整解析、分块、唯一抽取profile还是查询配置。实体多或上下文短不作为质量目标。当前交付用户检查后，再根据具体问题确定必要候选；改配置不会更新已生成图谱，也不应删除回执盲目重导。

原生 `/query/data` 可查看实体、关系、片段及引用，不生成最终答案，但关键词提取等仍可能调用模型。分别请求data和answer会独立执行，不能把前者自动当作后者实际使用的上下文。源码中的产品专属业务逻辑保持零新增。

## 证据指针SDK原型

`evidence_extract.py`接入官方`RoleLLMConfig.func`。flash输出实体、关系及`evidence_ids`，适配器校验后从原文区间复制完整文本，转换为原生JSON；原生文档流水线继续负责片段、图、向量及来源跟踪。产品专属名称在边界统一使用已核产品前缀；原文中无法确认产品身份时拒绝。类型支持可由已核证据目录声明，不兼容的模型类型拒绝，不由程序改写保险规则。

证据目录只存原文区间、编号及可选类型支持，正文从已验摘要的原件读取；证据须实际位于本片段内。原文单元完整性仍需检查，合法编号不能证明模型选对了证据或关系。类型指导和选择规则共用`entity_type/products.yml`，中间指针结构不扩展原生图谱字段。

合并回调依据已验证抽取结果的证据记录复制、去重原文，按来源文件和原文位置排序，不调用模型重述。回调前被原生长度筛选省略的已选证据可由该记录恢复；未知模板、自由改写或其他对象的证据拒绝。记录依赖本次新目标导入过程，当前操作器不自动恢复既有工作区或重放未知请求；截断和原生检索长度限制仍须核对实际结果。

准备批次须有`runtime.env`、原件/准备输入摘要、每片段证据目录及目录摘要。原型用以下独立入口，先预览，只有新目标才执行导入：

已有目标或上传回执时拒绝再次导入。原型记录在该批忽略目录的`evidence-events.jsonl`、`provider-calls.jsonl`、`contract.json`、`uploads.json`、`technical-verification.json`及`final-code-readback.json`。SDK完成后关闭存储再交接，既有原件和其他工作区保留。
