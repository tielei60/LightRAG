独立仓库基于官方 `v1.5.7`，提交 `28ff1b05f2ac3f3e6fa14dd2cd33656579bd0c9c`。

- `origin`：用户 fork `tielei60/LightRAG`。
- `upstream`：官方 `HKUDS/LightRAG`。
- `1.5.7`：保留官方基线。
- `codex/product-import-1.5.7`：产品配置、提示资源和操作支持。

本目录不修改 LightRAG 核心、解析器、抽取协议、检索或回答流程。使用官方 API 服务与原生 WebUI，首次只导入三款产品，由用户检查原文、图谱和问答。旧项目仅提供模型连接配置，不读取旧工作区。

## 配置与扩展

本批通过官方配置接入模型和提示，不引入平台业务依赖：

| 项目 | 本批选择 |
|---|---|
| LLM绑定 | 官方OpenAI兼容绑定 |
| 抽取、关键词、回答模型 | 明确配置为 `qwen3.8-flash`，关闭思考，temperature为0 |
| 向量模型 | `qwen3.7-text-embedding-flash`，1024维 |
| 存储 | 官方JSON、NetworkX、NanoVectorDB本地组合 |
| 新工作区 | `products_first3`，位于 `rag_storage/products_first3` |
| PDF | 官方legacy解析及R递归分块 |
| Markdown | 官方native解析及P分块 |
| 普通分块参数 | 1200 token、100 overlap；P采用官方独立默认配置 |
| 抽取语言和协议 | 中文、官方JSON抽取协议 |
| 抽取轮次 | `MAX_GLEANING=0`，即初次抽取后无额外gleaning |
| 单次抽取上限 | `MAX_EXTRACTION_ENTITIES=200`、`MAX_EXTRACTION_RECORDS=500`；官方默认是40/100 |
| 重排 | 本批未配置重排服务，保留原生检索，页面参数按实际能力使用 |

数量上限是每个片段的一次模型响应，不是每份文件或每个产品总量；调宽不等于不限量，也不要求凑满。图谱的描述合并等原生调用仍可能发生，“一次抽取”不代表整个导入仅调用一次模型。

自定义实体类型和关系指导位于 `product/prompt_profiles/entity_type/products.yml`，通过官方 `PROMPT_DIR` / `ENTITY_TYPE_PROMPT_FILE` 加载。优先保留产品归属、条件、否定、例外和原文支持，不拆出大量无用细事实。输出示例只描述官方结构，不添加虚构业务案例。

## 运行

在仓库根目录执行：

```sh
make -f product/Makefile start
make -f product/Makefile status
make -f product/Makefile preview
make -f product/Makefile import
make -f product/Makefile stop
```

`import`要求已存在准确的本机清单，核原件摘要、三个产品、官方版本及新目标后调用官方上传接口。已有上传回执时拒绝自动重放；中断或未知先核原请求，不删除回执来盲目再导。日志位于 `output/server.log`，进程号位于 `output/first3/server.pid`。

环境使用Python 3.12，安装依赖见 `requirements.lock`，再以 `uv pip install --no-deps -e .` 安装本仓库。原生WebUI静态制品取自同版官方wheel，放在Git忽略的 `lightrag/api/webui`；可以依官方说明重新构建。`.env`、inputs、rag_storage、output和真实原件均不提交到Git。

## 用户检查

先核文档状态，再查看实体/关系和来源片段，最后用已有问题提问，关注计划差异、责任选择前提、免责与例外是否正确。导入技术结果与用户业务验收分别记录；用户检查前不扩展至其他产品、不自动批量评分或反复调参。本机浏览器自动化当前不可用，页面可访问性由HTTP检查，实际交互由用户核验。

## 结构与效果检查边界

PDF的legacy解析保存展平文字，不提供逐页结构sidecar。与同一解析器输出一致只能证明提取结果已保存，不能证明表格行列、注释和全部图文完整。官方P分块依赖解析sidecar；没有sidecar会退为R，不能仅改一个分块参数就恢复PDF结构。Markdown的原生标题和表格结构也不能自动证明跨条款条件已完整。

检查按“原件→解析→片段→实体关系→实际上下文→原答”定位。先核原文是否读全、条件是否保留及产品归属，再判断应调整解析、分块、唯一抽取profile还是查询配置。实体多或上下文短不作为质量目标。当前交付用户检查后，再根据具体问题确定必要候选；改配置不会更新已生成图谱，也不应删除回执盲目重导。

原生 `/query/data` 可查看实体、关系、片段及引用，不生成最终答案，但关键词提取等仍可能调用模型。分别请求data和answer会独立执行，不能把前者自动当作后者实际使用的上下文。源码中的产品专属业务逻辑保持零新增。

## 京康优护上下文优化候选

独立候选入口：[http://127.0.0.1:9622/webui/](http://127.0.0.1:9622/webui/)，提问入口为同端口 `/workspace/`；工作区 `jingkangyouhu_context`。原9621首批工作区继续保留。本候选仅处理京康优护的条款、说明书和投核保规则，问题由用户自行提出和验证。

```sh
make -f product/Makefile BATCH=jingkangyouhu-context status
make -f product/Makefile BATCH=jingkangyouhu-context stop
make -f product/Makefile BATCH=jingkangyouhu-context start
```

`output/jingkangyouhu-context/runtime.env` 是候选私有配置，启动时只传给该进程。清单、逐份受理回执、准备后的请求、原文范围映射和检查记录均在同一忽略目录。已有回执禁止盲目重导。

`prepare_context.py` 接受经过检查的原文边界，读取PDF原文或Markdown，在每个片段添加经原件核实的产品名称、文件名和物理页范围，原文正文不改写。边界清单与摘要验证后，使用官方 `/documents/text` 的 `fixed_token`、`split_by_character_only` 保持片段，不替换内部函数；超过声明的8192 token上限会明确失败，不静默再切开。本候选最大片段低于2500 token；上限是接口的输入兼容参数，不是调用预算。

条款按已检查的完整条款边界准备，保险责任2.5含基本/可选责任及年龄、选择前提，职业或工种变更6.4保留完整通知义务和三个分支。释义整体保留，说明书与投核保规则各整体保留，因此不会因进一步切分丢掉其计划对应表。此安排适用于本批实际长度，未声称自动适用所有产品。边界及产品身份作为本机资料清单，不写进业务代码。

抽取仍使用唯一 `entity_type/products.yml`，增加Rule类型及产品限定命名、计划—责任—规则关系指导；共享责任可共用，不同适用条件须分清，不能为了连通而虚构关系。原生回答附加指导位于 `user_prompt/products.md`，通过 `USER_PROMPT_PREFIX_FILE` 加载，要求计划未明确且有差异时区分说明，不能默认选择或混用规则。用户仍需检查实际回答是否遵循。

候选是“输入上下文＋条款边界＋提示指导”的组合改进，不将效果单独归因于提示。没有迁移旧图/缓存、手工补边或修改LightRAG核心。原生来源文件名指向原件身份，但文本导入不会上传原件下载副本；完整原件仍在原只读目录，PDF页码指物理页而非页脚印刷页码。原生图和来源可用于检查，不能把连接数增加当作语义验收通过。

## 责任范围修正候选

后续针对真实检查中发现的责任规则串用，候选入口为 [http://127.0.0.1:9623/webui/](http://127.0.0.1:9623/webui/)，工作区 `jingkangyouhu_scope`，使用 `BATCH=jingkangyouhu-scope` 管理启停。旧工作区及既有原答保留，不能把修改提示后的新回答冒充旧对照。

本候选将保险责任内部按原文责任标题进一步分段，住院医疗、住院前后门急诊、住院津贴分别保留完整规则。已核实的共同选择前提从同文件上级原文区间附入；上级内容和本段正文分别标示并记录来源范围。准备工具要求责任标题实际存在于该片段、上级范围在本段之前且锚点相符，不按产品名称判断业务。正文范围仍完整覆盖原提取全文，附入上下文的重复范围单独登记。

唯一通用抽取提示要求局部规则名称、描述和关系端点保留责任范围，不能从共享免赔额或保额推导其他规则共享。通用回答指导要求先核错误前提、明确条款限制、保持基本/可选分类和比例基数一致；图关联须经原文标题及范围核实后使用，不将单项责任延续解释为整个合同延长。未写入七道测试题的固定答案或逐题处理代码。

检验是组合改进：输入责任边界、抽取指导及回答指导共同调整，分别保留旧/新原答及源文核对，不把效果单独归因于某一项。真实验证使用已固定的七题，保持模型、mix模式、重排关闭及空历史；范围外问题仍待用户检查。

## 原文证据候选

`BATCH=jingkangyouhu-evidence` 对应9624端口、`jingkangyouhu_evidence`工作区，仍仅处理京康优护三份原件。抽取按用户要求固定使用`qwen3.8-flash`；问答单独配置为`qwen3.8-max`。模型切换仅使用官方角色配置，既有候选不会因文件修改自动完成重抽或验收。

本候选以完整原文句子/表格行为抽取描述依据，保留产品限定名称及原文支持的上位归属；替换冗长指导，不追加七题专用规则。`prepare_context.py`的来源包装只保留身份、位置及真实原文标题，已移除解释性范围指导。正文及已核父区间仍保留；这些改变均不修改核心，也不手工写图。

仅检索检查使用原生`/query`的`only_need_prompt=true`取得当次完整组装提示，同时核实际图关系和原文。诊断请求不冒充历史回答当次上下文；回答正确也不代替输入质量验收。抽取描述仍可能不遵守摘录要求，是否生效以该批忽略目录中的核查记录为准，不能把提示要求当作保证。

长释义进一步按真实定义边界检查的候选使用`BATCH=jingkangyouhu-definitions`、9625端口及`jingkangyouhu_definitions`工作区。与原文证据候选相比，仅调整已审边界：28个定义分别保留，住院医疗费用的9个子项附入同条款的共同范围原文；三份资料共71片段。边界属于忽略目录中的本批资料清单，不加入产品专用分支。抽取仍为flash、问答为max；既有检查结果和待核项分别保留，入口可访问不等于输入或业务验收通过。

当前检查入口为 [9625 WebUI](http://127.0.0.1:9625/webui/)。该候选仍供诊断：细分定义有助于保留排除条件，但不能保证模型抽出上位归属关系。检查必须同时覆盖正文保真、条件完整和实际关系，不能只统计孤立节点或片段命中。完整定义与共同范围应作为分块单元的优先考虑；不通过人工补边、扩大模型或增加逐题提示掩盖缺项。实际完成状态、已知问题和验收证据统一记录在平台仓库对应 OpenSpec `tasks.md`，本文件只说明运行和检查方法。

完整定义条款比较使用`BATCH=jingkangyouhu-clause`、[9626 WebUI](http://127.0.0.1:9626/webui/)及`jingkangyouhu_clause`工作区。7.6共同范围和九项费用保留在一个正文单元，其他边界不变，共62片段；仍为flash抽取、max问答、MAX_GLEANING=0。该入口用于诊断，不代表已适合批量导入。产品归属、条款内部关系及原文条件分别检查，不能依赖目录恰好被抽出许多关系来证明完整性。

官方MAX_GLEANING为正值时会使用extract角色追加一次补查；新增调用会读取原文及上次输出，需比较真实收益与用量。它不是按质检结果只处理缺陷片段的自动修复开关，同名描述的原生合并也不提供语义正确保证。隔离补查结果只留诊断证据，不直接写回现有图谱。

原文层级附入只能使用同文件可核的真实标题/区间，现有prepare工具支持此输入方式；它不保证模型建立产品连接。评估时分别核业务条件、实际关系、来源限定及引用纯净度。孤立节点仅作为检查线索；定义完整、产品及来源明确的节点，不为连通性统计强行补边。样本未证明改进稳定时，保留诊断结果，避免直接扩大为整款重处理。

## 证据指针SDK原型

`evidence_extract.py`接入官方`RoleLLMConfig.func`。flash输出实体、关系及`evidence_ids`，适配器校验后从原文区间复制完整文本，转换为原生JSON；原生文档流水线继续负责片段、图、向量及来源跟踪。产品专属名称在边界统一使用已核产品前缀；原文中无法确认产品身份时拒绝。类型支持可由已核证据目录声明，不兼容的模型类型拒绝，不由程序改写保险规则。

证据目录只存原文区间、编号及可选类型支持，正文从已验摘要的原件读取；证据须实际位于本片段内。原文单元完整性仍需检查，合法编号不能证明模型选对了证据或关系。类型指导和选择规则共用`entity_type/products.yml`，中间指针结构不扩展原生图谱字段。

合并回调依据已验证抽取结果的证据记录复制、去重原文，按来源文件和原文位置排序，不调用模型重述。回调前被原生长度筛选省略的已选证据可由该记录恢复；未知模板、自由改写或其他对象的证据拒绝。记录依赖本次新目标导入过程，当前操作器不自动恢复既有工作区或重放未知请求；截断和原生检索长度限制仍须核对实际结果。

准备批次须有`runtime.env`、原件/准备输入摘要、每片段证据目录及目录摘要。原型用以下独立入口，先预览，只有新目标才执行导入：

```sh
make -f product/Makefile BATCH=jingkangyouhu-pointer-scoped evidence-preview
make -f product/Makefile BATCH=jingkangyouhu-pointer-scoped evidence-import
```

已有目标或上传回执时拒绝再次导入。原型记录在该批忽略目录的`evidence-events.jsonl`、`provider-calls.jsonl`、`contract.json`、`uploads.json`、`technical-verification.json`及`final-code-readback.json`。SDK完成后关闭存储再交接，既有原件和其他工作区保留。

该入口目前验证四类摘录，不是整款资料；实际完成事实由对应OpenSpec tasks记录。SDK使用原生`ainsert`与`aquery`，当前HTTP上传服务尚未接入适配器，不能把普通`start/import`当成证据指针导入。真实试查沿用已授权问题，仅生成检索上下文；问答生成另行核输入完整性。角色为抽取/关键词flash、问答max，抽取不回退max。

## 外置证据对照实验（独立入口）

本次新增 `python -m product.evidence_trial prepare/replay/live`，用于在不修改 LightRAG 核心的前提下，对同次原生检索结果做文档范围校验、原文证据补齐与一次生成对照。它不替代原生 `/query`、WebUI 或已有证据指针导入，也不新增平台产品主数据。

先按 [外置实验操作说明](trial_examples/RUN-zh.md) 跑无密钥离线样例，再在本地审核资料范围并显式配置模型。完整设计、已实现范围和未实施项见 [保险产品优化方案](../docs/InsuranceEvidenceOptimization-zh.md)。真实原件样例默认未审，不把定位测试当成业务准确率。每次实验保存完整问题、检索结果、证据、提示、答案及异常；原生API未暴露的阶段明确标为不可取得。
