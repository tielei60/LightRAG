# LightRAG 1.5.7 保险产品导入链路详细设计

**独立导入专项 V1.0｜2026-11-11**

> 目标：真实产品资料导入后，不依赖问答平台、不依赖自定义查询补证服务，使用固定配置的 LightRAG 原生查询，能够定位所需的责任、计划、规则和原文依据，并保留影响结论的条件。
>
> 本文只设计导入链路及其检索验收。暂不做平台接入、SDK/HTTP 入口统一、会话理解、查询路由、在线范围过滤或在线证据补全改造。它是《独立开发与验收方案 V3.0》的导入专项，不是要求同步实施 V3.0 的全部任务。

## 0. 阅读说明与依据边界

设计沿用已审查仓库 `tielei60/LightRAG` 的 `codex/product-import-1.5.7` 分支快照，提交为 `714c2bf17ebf7864d046fe42485e4f6edfdde79a`。本次复核了该快照的准备、证据抽取和导入代码，并核对官方 `v1.5.7` 的查询参数及合并逻辑；不把它称为分支此后最新状态。[S2–S6]

本文中“已有”指上述代码或前版方案明确记载的能力；“本轮要求”是拟开发设计；“建议初值”需要实测，不是版本默认值或已达到的效果。真实产品示例以仓库 Markdown 为依据；本次没有逐页核验 PDF 原件，没有运行模型导入和问答回归。[S7]

早期端到端方案中的平台编排、产品主数据和结构化事实优先链路不作为本轮任务。保留的是“具体产品事实必须有依据，不得用常识补齐”的边界。[S8]

**不能承诺仅改导入就保证任意问题绝对正确。** 导入的责任是让信息真实、范围正确、关系可定位、必要依据可被原生检索读到；是否找得到、是否进入实际生成上下文，必须通过固定原生查询实测。查全了但模型仍答错，应归为生成缺陷；不要通过反复重导掩盖。

## 1. 本轮唯一目标、交付范围与排除项

### 1.1 完成定义

在独立 LightRAG 环境中，用真实原件和最小身份清单完成导入，重新启动后仍能通过原生查询找到正确资料。验收必须同时回答：

| 层次 | 必须证明的结果 |
|---|---|
| 信息进入 | 责任、计划、限制、例外、定义、表格没有被遗漏或错列 |
| 归属正确 | 不同产品、版本、计划和责任没有被错误合并或扩大适用范围 |
| 原文可追溯 | 每项关键事实能回到明确的文档版本和原文位置 |
| 原生可召回 | 关键内容实际进入原生片段、图或向量，而非只在旁路 JSON 中存在 |
| 上下文够用 | 原生查询返回的最终上下文含本题所需的完整依据，不只命中一句结论 |

“导入成功”“图谱节点很多”“JSON 合法”“模型说自己有把握”，均不能单独证明上述结果。

### 1.2 本轮开发内容

工作集中在资料盘点、结构解析、原文范围映射、完整检索单元、中文实体关系抽取、证据校验、范围命名、合并保真、原生写入、读回与检索验收。缺少的产品身份和文档版本由本地清单模拟，不连接平台。

本轮只选择一个正式导入路径：以仓库已有 `product/evidence_import.py` 的 SDK 导入原型为基础推进。导入完成并关闭写入进程后，通过原生 SDK 查询或原生服务读取该工作区验收，不要求重建统一上传接口。

### 1.3 本轮不做

| 明确排除 | 说明 |
|---|---|
| 平台联调、产品后台、会话和意图识别 | 平台工程完全不参与 |
| 自定义统一导入/问答 API | 不作为本轮交付或验收前置条件 |
| 原生查询算法重构、在线补证、逐题检索分支 | 查询是固定测试工具，不是本轮改造主体 |
| 第二套完整事实库、规则执行引擎 | 补充记录只服务于导入保真、身份和溯源 |
| 权限、费率/现金价值计算、核保决策、多模态/OCR | 继续保持既定范围 |
| 所有存储后端适配、生产部署、复杂增量发布 | 沿用当前本地存储，用新候选批次验证 |

不做费率计算，不等于删除条款中的比例、赔付公式、限额或时间。它们属于原文含义，必须保留；本轮不自行设数计算。

## 2. 现有基础与本轮真正要补的地方

| 已有基础 | 本轮继续使用 | 需要补齐的缺口 |
|---|---|---|
| `prepare_context.py`：原文区间、前置父级、标题、页码、拼回检查 | 原件不改写、位置校验、分隔符保持边界 | 从人工边界进一步形成结构候选；支持后置定义、完整表格和明确引用 |
| `evidence_extract.py`：模型选择证据编号，程序复制原文 | 不让模型自由编写事实描述 | 计划/责任范围；完整条件；中文类型；编号真实与语义正确分开检查 |
| 产品前缀和关系端点检查 | 降低跨产品混合 | 同产品不同计划、责任、版本仍需不同身份 |
| 原文合并回调及内存台账 | 避免不必要的模型概述 | 持久化来源、按位置而非文字去重、缓存恢复、合并后读回 |
| `evidence_import.py` 调用原生 `ainsert` | 保留原生文档、图、向量和状态处理 | 正式的预检查、全批次状态和导入后检索验收 |
| 原生 `only_need_context` / `only_need_prompt` | 用来检查真正能返回的检索上下文 | 不把另一条请求的上下文冒充某次回答实际使用的内容 |

以上代码基础来自固定快照。[S2–S6] 特别注意：当前 `EvidenceChunk` 限制证据属于同一来源；跨文件组合不是现成能力，不能直接取消校验后声称已支持。[S3]

**本轮最重要的改变：在导入时把必要上下文落到原生可检索内容中，而不是依赖未来查询时再从旁路台账补回来。**

## 3. 导入总链路与阶段输出

```text
真实原件＋最小身份清单
    ↓
01 盘点、身份/版本确认、去重与排除登记
    ↓
02 结构化文字解析，保存原文及位置
    ↓
03 建立标题、表格、计划、责任与引用范围候选
    ↓
04 组织完整检索单元：主规则＋必需前提＋相关例外
    ↓
05 给原文证据编号，生成抽取输入
    ↓
06 中文实体关系抽取：选择对象、范围及证据
    ↓
07 检查真实性、关系支持、范围、条件与覆盖
    ├─ 有缺陷 → 局部修正一次 → 仍不通过则停止该批验收
    ↓
08 将核准结果映射为原生实体关系与真实检索片段
    ↓
09 通过原生文档流水线写入片段、图、向量与来源
    ↓
10 持久化、关闭写入进程、重新读回
    ↓
11 固定原生查询验证：找得到、范围对、条件全
    ↓
12 导入验收通过，或明确记录未通过原因
```

| 阶段 | 主要输出 | 不通过时 |
|---|---|---|
| 01 | 文件清单、身份记录、排除与重复记录 | 不开始模型抽取 |
| 02 | 结构化块、原始解析文本、位置映射 | 仅修复相关页/表/段 |
| 03 | 范围候选、引用依赖、待确认项 | 不把未知解释为通用 |
| 04–05 | 原生待导入片段、证据目录、长度报告 | 不静默再切断条件 |
| 06–07 | 核准抽取结果、覆盖和缺陷报告 | 不将未核准结果作为可用图谱 |
| 08–10 | 原生索引、来源映射、读回报告 | 候选批次不进入验收通过状态 |
| 11–12 | 逐题检索报告、批次结论 | 区分导入缺陷与检索/生成缺陷 |

## 4. 输入资料：只模拟身份，不模拟知识答案

### 4.1 每份文件的最小清单

| 信息 | 来源与处理 |
|---|---|
| 产品标识、正式名称 | 平台只读导出或本地测试清单；与正文身份核对 |
| 产品业务版本 | 有依据才填写；未知明确记录，不能以下载日期代替 |
| 文档标识与修订版本 | 独立于产品版本；原件摘要绑定具体文件 |
| 文档角色 | 条款、说明书、计划表、特别约定、投保资料等 |
| 文件路径、SHA256 | 程序生成，保留原件只读 |
| 关联资料 | 经确认的基础条款/附件/特别约定关系；不是所有同目录文件都自动适用 |
| 文件级适用范围 | 仅限正文、标题或经过核对的明确资料声明支持的范围 |
| 是否进入本批 | 纳入、排除、待确认，以及具体原因 |

产品族、销售别名只在已确认且与本批有关时记录。不能因为“内容很像”就把两款产品视为同一底层产品，也不能凭文件名推断某份条款适用于所有销售计划。

### 4.2 资料去重

字节相同的重复下载可合并导入一次，保留多个获取来源。PDF 与由其转换的 Markdown 即使字节不同，也应记录为“同一资料的不同表示”，核对后选择一个解析入口，避免作为两份独立权威证据重复加权。

不同版本或不同产品中出现相同文字，不能据此合并文档身份或事实归属。相同正文可以共用物理存储，但来源、版本、计划和引用仍需独立。

### 4.3 排除项与缺件

费率表、现金价值表、扫描件等按本轮边界排除并登记。混合资料中的产品责任、比例和限制不能因为文件名含“核保”或“保费”就被无提示删除；保留用于规则解释的原文，不开发核保或费率执行。

某个问题所需的条款、附件或定义没有提供时，记录缺件，不让模型用说明书概括或行业常识补齐。冲突资料也不得用“最近上传优先”或统一文档排名自动调和。

## 5. 解析层：先把结构读对，再谈实体关系

### 5.1 三类数据同时保留

| 数据 | 保存目的 |
|---|---|
| 原始文件 | 最终核对依据，不覆盖、不改写 |
| 原始解析文本/单元格文本 | 稳定的原文比对基线，记录解析器与版本 |
| 结构化块及位置映射 | 表达标题层级、段落、条款、表格、脚注及原件位置 |

可以做换行整理、重复页眉标记等阅读处理，但必须保留处理前后映射。不能对已经修改过的字符串继续使用原解析文本的偏移量。

PDF 使用物理页编号；只有确有依据时才另外保存印刷页码。DOCX/Markdown 不虚构页码，优先使用标题路径、段落号、表格行列及字符区间。

### 5.2 格式处理边界

| 格式 | 本轮处理 |
|---|---|
| Markdown / TXT | 识别标题、列表、表格及正文；不假定排版一定规范 |
| 文字 PDF | 复用已有文字解析，增加关键表格、脚注与阅读顺序核验 |
| DOCX | 当纳入验收样本时，使用受控的段落与表格解析，保留顺序和合并单元格关系 |
| DOC | 受控转换后处理，保留原件与转换记录；不能可靠转换则标记不支持 |
| 扫描件或关键文字无法提取 | 本期阻断/排除，不临时引入 OCR/VLM |

不为了覆盖所有格式另写一个解析平台。当前准备工具只直接支持 PDF、Markdown、TXT，其他格式属于拟增加的受控处理，不是现有能力。[S4]

### 5.3 特别检查表格和脚注

计划表里的一个值必须绑定表名、列计划、行责任和适用脚注。空白、破折号、数值0和“未提供”要分别保存，不能统一解释为“不保”。合并表头要恢复到对应列，跨页表头要关联，不能把上一页的注释遗漏。

**表格行完整不等于事实完整。** 计划名称在表头、责任在首列、限制在表下时，三处需要能一起还原。

### 5.4 解析验收

程序检查空页、乱序迹象、缺失表头、引用断点、可疑字符和段落覆盖。人工优先核对会影响结论的计划表、金额/比例、否定词、例外句、责任标题与跨页内容。

“所有片段能拼回解析文本”仅证明准备过程没有丢字；不能证明 PDF 本身解析正确。两类检查分别记录。

## 6. 适用范围：把“这条规则属于谁”说清楚

### 6.1 最小范围信息

| 维度 | 规则 |
|---|---|
| 产品/版本 | 每个产品专属事实均有身份边界；未知版本不与已确认版本自动合并 |
| 保障计划 | 只来自原文明示计划、表格对应或明确适用说明 |
| 保障责任 | 来自责任标题与正文关系；不能用最近的同名词猜归属 |
| 基本/可选类别 | 独立维度，不把“可选责任”当成一个计划 |
| 条件、对象、时间和例外 | 保留原文逻辑和证据，不急于转成可执行表达式 |
| 证明范围的原文 | 与证明具体约定内容的原文分别记录 |

四种状态必须区分：明确通用、明确局部、该维度不适用、尚未确认。**尚未确认不等于通用。**

### 6.2 范围沿真实结构继承

文件身份可以提供产品归属；计划标题只能约束其真实范围内的条文；共同前提可以沿明确标题层级向下传递。章节切换、责任切换、表格列切换时重新确定范围。

“免赔额相同”“同属一个产品”“两项责任相邻”“图上连通”，都不足以证明其他规则也共同适用。

正文没有计划维度时，先保留责任级规则。另一份资料明确了计划—责任对应关系后，可以分别记录该映射和责任规则；不能在没有证据的情况下直接生成一条“所有计划都适用”的事实。

### 6.3 有效组合不能任意交叉

原文只支持“计划一＋责任甲”和“计划二＋责任乙”，就保存这两个组合。不能用独立的计划列表和责任列表自动生成四种组合。

共性责任可以使用一个经过确认的共享节点；只有适用范围或规则不同才拆开。不为了形式上的隔离，把每个共性句子按全部计划复制一遍。

### 6.4 范围不能只藏在台账中

本轮不改在线查询去读补充台账。因此，已确认的范围需要同时体现在：

1. 原生检索片段里的产品、版本、真实标题和范围证据。
2. 原生实体/规则的可辨识名称及证据描述。
3. 有原文支持的产品—计划、计划—责任、责任—规则关系。

补充记录负责详细追溯和校验；它不是检索时自动生效的过滤器。**产品前缀和范围文字能减少混淆，但不是硬过滤保证；必须通过混库测试验证。**

## 7. 核心设计：形成可以直接检索的完整证据单元

### 7.1 三个层次不要混淆

| 层次 | 含义 | 是否直接参与原生查询 |
|---|---|---|
| 原文证据片段 | 某一来源的完整句、段、表格区域或定义，带原文位置 | 作为检索单元正文的一部分 |
| 完整检索单元 | 围绕一个业务主题，组合正文和不可缺少的前提/例外 | **必须写入原生 text chunk 并建立向量** |
| 抽取工作上下文 | 提供识别结构、引用和范围所需的信息 | 只有写入检索单元的证据才可作为该单元原生来源 |

抽取模型看过某条限制，但原生 chunk 中没有该限制，不算解决证据完整性。最终抽取输出所选业务证据必须出现在对应原生片段中；否则先重编片段并重新校验，不让图描述引用一个查询看不到的外部依据。

### 7.2 检索单元的组成

```text
【来源标识：整理信息，不是合同新约定】
产品/文档版本/原文位置/真实标题路径

【主原文】
一项完整责任规则、一个计划映射区域或完整定义

【必要前提原文】
同一责任的共同前提、选择条件或时间对象

【本项限制与例外原文】
与本项结论不可分开的否定、例外、限额及终止条件

【明确引用的原文】
会改变本项含义的定义、表格脚注或相关条文
```

以上栏目是组织结构，不生成新的保险结论。每块保留自己的来源编号，原文按完整区间复制，不把分散字词拼成原件没有出现过的“完整句”。

### 7.3 按内容类型组织

| 内容 | 建议组织方式 | 必须避免 |
|---|---|---|
| 保障责任 | 一项责任或一个完整分支，带共同前提及相关例外 | 所有责任全文混在一个超大片段；或每句话切一片 |
| 计划对应 | 保留表头、计划列、责任行及注释；小表优先整体保留 | 只存计划名或单独数值 |
| 条件规则 | 主条件、结果、否定/例外及数值基数同片保留 | “约定比例的60%”只留下“60%” |
| 多分支给付 | 总领句＋当前分支完整条件和结果；全分支结构另可检索 | 只留金额，丢年龄分界或“保单周年日” |
| 费用定义 | 定义总领句、组成项及排除条件可完整还原 | 把费用子项当成新增保障责任 |
| 通用免责 | 独立完整组织，保留适用对象；与明确引用的责任建立联系 | 不问范围就把全部免责塞进每个片段 |

### 7.4 必需依赖与补充依赖

**必需依赖**是离开它就容易改变当前条款含义的内容，如可选前提、比例基数、同条款的例外、表格脚注。优先在导入时随主原文一并编入。

**补充依赖**是解释更广问题时可能需要的较长定义、其他条款或全部免责。保留为独立可检索单元和有证据的关系，不无限展开全文。测试问题需要它时，必须检查原生查询是否一并找到了；不能仅因目录里有依赖编号就宣布完整。

依赖有环时按证据编号去重；不无限递归。是否必需根据原文结构和业务含义确定，不根据某道已知测试题临时编排。

### 7.5 跨文件内容如何处理

优先保留同源完整单元及原文支持的关系。确需让计划表与另一份条款共同进入一个检索单元时，可在导入阶段创建少量“组合证据材料”，但必须满足：

| 条件 | 要求 |
|---|---|
| 文件关联成立 | 同一已确认产品/版本或明确的附件关系，不仅是名称相似 |
| 每段原文独立追溯 | 各有文档、版本、位置、摘要及原文 |
| 不生成新推断 | 同时展示计划映射与责任规则，不把两段并列误写成额外约定 |
| 原生来源透明 | `file_path` 指向真实保存的组合材料；正文明确列出各原件，不冒充单份合同原件 |
| 适配器校验升级 | 用来源白名单和逐段校验替代“单一来源”限制，而不是直接取消来源检查 |
| 更新连带处理 | 任一原件变更，都使该组合单元失效并重新准备 |

组合材料是可追溯的原文容器，不是模型生成的问答卡。没有必要就不创建，避免重复证据占满 Top-K。当前代码仍是同源约束，以上是新增设计。[S3]

### 7.6 长度策略

先按业务单元确定边界，再计算实际 token。可把普通检索单元约800–1800 token、较完整责任/定义约1800–3000 token作为首轮观察区间；它们是候选范围，不是要求每片达到的长度，也不是版本默认值。

硬上限应同时满足抽取输入＋系统提示＋输出预留、embedding 输入以及预设原生查询预算。不能照抄原型中的8192作为万能上限，也不能用中文字符数直接代替token。

超限优先沿原文分支拆分，并为每个子单元保留完整共同前提；不能在“但、除外、仅限、上述”之前截断。若关键规则无法在既定预算内安全组织，登记阻断项，不静默依赖未来在线补证。

### 7.7 主单元与上下文副本

每个原始规则指定一个主要归属单元。附入其他单元的共同前提、定义和标题，标记为“上下文引用”，不得每出现一次就重复生成一套事实和关系。

原始正文覆盖与上下文复制分别统计。正文一次完整覆盖，依赖可以有限重复；不能把重复引用次数当成更多独立证据或更高业务置信度。

## 8. 中文实体关系抽取：少做自由概述，多做有依据的识别

### 8.1 实体类型收敛

建议业务类型统一为：**产品、保障计划、保障责任、责任选择条件、合同规则、术语定义、机构、其他**。实体名称、类型值、关系关键词、描述和检查原因使用中文；原生JSON协议键、程序标识和原文已有字母名称不强行翻译。

不需要把“15天”“60%”“某个年龄”都做成独立通用节点。它们通常应留在所属规则的原文中，连同对象、条件与基数一起保存。

### 8.2 模型与程序各自负责什么

| 模型负责 | 程序负责 |
|---|---|
| 识别当前主单元中确实存在的实体和直接关系 | 检查类型、端点、范围、引用是否合法 |
| 从候选范围中选择有原文支持的归属 | 生成短而稳定的存储身份，检查规范化与长度碰撞 |
| 选择正文、范围、前提和例外的证据编号 | 按原文区间复制，不自由改写描述 |
| 对模糊、冲突或无法确定的事项提出待核原因 | 不让未知范围默认为通用，不让不合格单元混入正式验收批次 |

现有 `PointerEntity` / `PointerRelationship` 可以继续作为基础；范围信息在适配层扩展并核对后，再映射回原生协议。不能只给原生JSON增加任意 `scope` 字段，就认为原生存储和查询会自动使用它。[S3、S6]

### 8.3 抽取输入需包含

本单元的产品/文档身份、主原文、必要上下文、证据目录、真实标题/表格位置，以及哪些内容只是上下文副本。候选计划或责任必须能对应原文；不能把标准答案中的关系清单当作候选输入。

对范围不清的单元，模型可以输出“待确认”与证据，但不能自行填完整。对名称未命中的别名，也不能靠常识自动创建销售关系。

### 8.4 每条关系需要两种依据

**关系内容依据**证明两端存在什么联系；**范围依据**证明联系适用于哪个产品、版本、计划和责任。

例如“计划二包含某责任”需要计划对应表或明确陈述；“该责任受某项规则限制”需要相应责任标题、正文及共同条件。不能因为两端都在同一文档中就补边，也不能为了减少孤立节点补出产品规则。

标题可以支持真实层级归属，但不能单独证明给付条件、保障范围或计划包含关系。对于程序可以确定的真实标题从属，可以登记结构连接；必须标明依据是文档结构，不将它升级为未经证明的业务适用关系。

### 8.5 防止定义误当责任

“药品费、床位费”等若出现在释义或费用组成表中，类型应是术语/费用定义，而非自动认定为一项独立保障责任。是否属于某责任，需要实际责任正文对费用范围的引用。

“基本责任、可选责任”是责任分类，只有原文明示命名的计划才创建保障计划对象。保险责任名称相同而适用条件不同的，按范围分别表达规则，不统一概述成一个无条件结论。

### 8.6 抽取提示的最小约束

```text
只识别本单元主原文及明确引用中有依据的实体和直接关系。
产品、计划、责任分类与费用定义不得混淆。
名称用于定位，证据用于证明；不得用自由概述替代原文条件。
每项业务规则选择完整正文及必需前提、否定、例外和比例基数证据。
上下文副本用于理解，不重复制造独立事实。
范围未确认时输出待确认，不推定通用。
不计算、不判断个案承保或赔付、不为了数量补关系。
```

提示词只定义通用抽取方法，不加入京康优护等产品的固定答案或逐题补丁。更换模型不是本轮第一步；先固定现有抽取模型和参数，确认输入与证据组织是否解决问题。

## 9. 图谱身份与合并：把不同规则分开，把同一原文保住

### 9.1 可检索名称与唯一身份同时兼顾

原生名称仍需保留可检索的产品、计划、责任和规则原称；不能全部换成模型看不懂的随机ID。内部唯一身份再结合产品/版本、范围和规则原文位置生成短标识。

示意命名，不代表真实条款事实：

```text
产品全称｜计划一
产品全称｜某责任
产品全称｜计划一｜某责任｜某规则〔短标识〕
产品全称｜计划二｜某责任｜某规则〔另一短标识〕
```

名称中的范围只能来自已经核准的范围记录。原生名称存在长度处理，必须在写入前检查字符、UTF-8字节、规范化及截断后是否碰撞；发生碰撞时重新生成短名，而不是继续写入。[S6]

### 9.2 有条件差异才建立独立规则节点

简单的产品—计划、计划—责任可以直接连边。不同计划或责任下的等待期、选择条件、给付规则等存在差异时，使用独立规则节点，避免让一对端点承载多套不同约定。

原生合并以实体名和端点对为重要依据，关系端点按无向方式归集；不能假定只增加关键词就能保存同端点多条独立规则。[S6]

典型结构：

```text
产品 → 计划 → 责任 → 有范围的规则
                       ↘ 明确引用的定义
```

箭头仅表达业务理解顺序，不表示原生无向图已经成为规则推理引擎。生成答案仍必须回到原文。

### 9.3 各类节点的描述边界

| 对象 | 描述应保存什么 | 不应保存什么 |
|---|---|---|
| 产品 | 原文产品身份、必要资料身份 | 全部条款与全部免责 |
| 计划 | 名称和支持计划构成的原文 | 所有责任细节的长篇拼接 |
| 责任 | 责任原称、类别和简明范围依据 | 每一项条件的无限累计 |
| 局部规则 | 完整小规则及必要条件证据 | 被概述后丢失条件的“短答案” |
| 术语定义 | 总领句、相关组成/排除内容 | 无来源的行业解释 |

主要细节在范围明确的规则和原生检索片段中保留。减少大节点描述，可以同时降低跨责任混用和检索上下文膨胀。

### 9.4 合并的明确规则

同产品、同版本、同范围、同规则身份的重复表述，允许关联多个来源；不同范围不合并。内容冲突保留各自原文和冲突记录，不让摘要模型挑选或调和。

证据去重按“文档版本＋解析版本＋位置”管理，不能只按规范化文本作唯一键。相同文字在两个来源中仍然是两个来源。展示去重不等于溯源去重。

现有原文合并回调可以继续使用，但要补持久化和来源核对。聚合只允许使用当前实际参与该对象写入/合并的已核准贡献，不能从整个批次台账随意恢复尚未绑定 `source_id` 的内容。缓存命中时也要能还原相同的贡献集合。

### 9.5 防止“抽取保真、合并后丢失”

原生链路存在描述合并、摘要预算和向量内容长度处理。[S6] 因此验收需要比较：抽取输出 → 原生合并结果 → 向量索引内容 → 查询上下文。

优先通过局部规则身份、小而完整的描述和上下文副本去重避免超长。不能把所有限制都藏在超长描述尾部，再依赖自动截断。原型中的64 token摘要阈值用于合并路径检查，不应作为本轮条款长度或最终优化参数。[S2]

若回调不能可靠识别当前合并对象及证据贡献，必须明确失败或局部调整导入聚合接入，不能靠字符串猜测或返回全局原文掩盖。需要的接入限于导入，不扩大为查询框架改造。

## 10. 五项质量检查与局部修复

### 10.1 检查清单

| 检查 | 程序可验证 | 仍需语义/人工核验 |
|---|---|---|
| 真实性 | 编号存在、原文区间和摘要一致、内容确实进入片段 | 解析是否忠于原件版面 |
| 范围 | 身份完整、已核范围存在、不同范围不碰撞 | 该范围是否真的由正文/表格支持 |
| 关系 | 端点存在、受控类型、没有非法自关联 | 原文是否支持该联系，而非仅共现 |
| 条件完整 | 所需依赖存在、原句未截断、数字和否定词保留 | 是否遗漏其他改变结论的条件 |
| 覆盖 | 标题/计划表/定义清单逐项有处理状态 | 是否有整项责任或脚注被错误标为可忽略 |

模型自检可以辅助找问题，不能作为独立正确性证明。关键计划表、责任选择、比例基数和局部例外，应进入人工核验的小型核心集。

### 10.2 覆盖清单从文档结构生成

建立“应处理单元清单”，来源于真实责任标题、计划行列、定义编号、例外列表和条款引用，不来源于模型抽出的对象数量。

每个单元标记：已进入原生片段；已建立所需实体关系；只需原文检索；待核；缺失；明确排除及理由。不是所有文字都必须变成图节点，但每项关键责任、计划映射和局部约定必须有可解释的检索落点。

目录和正文重复标题应区分。目录可辅助结构识别，不能代替规则正文进入事实描述；不能靠目录连了很多边，就宣布业务覆盖完整。

### 10.3 补抽流程有界

| 缺陷 | 优先处理 |
|---|---|
| 缺上级共同前提 | 补真实上级原文，重编本单元后重新抽取 |
| 计划表错列 | 修解析/结构映射，不反复调用抽取模型 |
| 漏一项实体或关系 | 定向复核缺失单元，不重抽全库 |
| 原文齐全但范围不确定 | 标为待核，不能自动猜一个范围 |
| 输出截断/协议错误 | 检查输入和输出预算，必要时沿完整业务分支拆分 |
| 描述被合并丢条件 | 修身份或聚合，不用回答提示词补回 |

每个缺陷单元本轮自动语义补抽最多一次，再失败进入人工待核；网络超时等技术重试另行计数，并明确未知结果不可盲目重复写入。直接调高 `MAX_GLEANING` 不等于实现这套定向流程；当前原型对额外带历史抽取有边界限制。[S2–S3]

### 10.4 不合格状态必须真的阻断验收

本轮不改在线查询识别旁路“待核”状态。**因此不能把不合格内容照常写入可用工作区，仅在检查文件里标为待核。** 向量召回仍可能读到那些片段。

本轮采取批次级处理：全部准备与预检查先在离线产物中完成；写入新候选工作区后，只有整批核心检查和检索验收通过才将其作为验收通过版本。部分成功可以供诊断，但不能声明产品已经完整可答。

不开发复杂发布系统；当前试验批次由操作者选择，失败候选保留用于定位，不覆盖已通过的基线。

## 11. 原生写入方式：先核准，再进入同一套原生流水线

### 11.1 采用一条导入路径，不先做统一接口

本轮使用已有 SDK 原型作为唯一受控导入路径，继续调用原生 `ainsert`。原生处理负责片段、实体关系、向量和文档状态，不绕过文档流水线直接改图数据库或向量JSON。[S2]

普通 WebUI 上传暂时不作为本轮质量路径。验收期间不从其他入口重新上传同一资料，也不要求把适配器接进所有HTTP上传路由。

### 11.2 推荐两段式导入

**准备与核准阶段**：完成完整片段、证据目录、范围、模型抽取与检查，保存逐片段的核准结果及指纹。

**原生写入阶段**：原生抽取角色回调仅为完全匹配的片段返回核准原生JSON；不再无条件调用模型重新抽一次。这样同一条知识不会在“预检查通过”后被第二次随机抽取改变。

这项“预抽取结果回放”是对当前原型的拟增加能力，不是现成开关。应保留原生片段与抽取缓存关联，不能通过写缓存内部文件伪造处理完成。

### 11.3 写入时的关键约束

| 约束 | 要求 |
|---|---|
| 片段一一对应 | 待写入文本、原生实际chunk和核准抽取结果的摘要可匹配 |
| 不被再次静默切片 | 沿用已验证分隔符/边界路径；超限明确报错，不更改边界后继续回放 |
| 身份与缓存一致 | 指纹覆盖原件、准备规则、证据目录、核准结果、提示/类型、模型和向量配置 |
| 原生来源真实 | 每条抽取事实选择的原文确实在关联chunk中；详细位置可回到原件 |
| 合并贡献可恢复 | 持久化核准结果和当前参与写入的证据集合；缓存不能使台账变空或过期 |
| 写入失败可定位 | 保存原生状态和已有回执，不删除回执盲目重放 |
| 单写入进程 | 本地索引导入时不与另一个服务进程同时修改同一工作区 |

若匹配失败，停止并记录，而不是降级成“再用默认模型抽一次”。当前 SDK 原型已经使用 `RoleLLMConfig` 与自定义抽取回调，可在此基础上扩展。[S2]

### 11.4 真正需要保存的位置

| 内容 | 必须进入的地方 | 原因 |
|---|---|---|
| 完整检索单元 | 原生文本片段及片段向量 | 原生查询能直接读到完整上下文 |
| 有范围的实体/规则 | 原生图及实体向量 | 用产品、计划、责任、规则名称定位 |
| 有依据的关系 | 原生图及关系向量 | 支持找到关联责任与规则 |
| 来源关联 | 原生source_id/file_path及真实chunk | 原生引用能回到实际检索内容 |
| 精细证据、位置、检查记录 | 本地派生台账 | 支持核验、复现和修正，不假装会自动进入原生检索 |

图、向量、片段三者缺一都要解释。不能仅手工插入图节点，却没有可查询的实体/关系向量或原文来源；也不能只导入增强文本，却让原生默认抽取把已经核准的范围覆盖掉。

## 12. 合并后读回：证明“实际存进去的是正确内容”

导入进程完成后，先完成存储落盘并关闭写入实例，再用新实例读取。若随后用原生服务验收，必须指向同一工作区并保持查询模型、embedding模型、维度和参数一致。

| 读回检查 | 判定方法 |
|---|---|
| 文档状态 | 纳入清单的文档均有明确结果；受理成功不等于处理成功 |
| 片段内容 | 与核准完整单元对应，关键前提/例外没有被再次切开 |
| 图对象 | 计划、责任、规则身份正确，不同范围未合并 |
| 描述 | 与核准证据一致，不是自由缩写或无依据概述 |
| 关系来源 | 两端、关键词、原文与source_id一致 |
| 向量对应 | 片段、实体和关系有对应可检索记录；不能只看图 |
| 引用 | 原生来源可定位；组合材料不冒充单份原件 |
| 完整性 | 关键责任、计划列、定义和限制没有缺项 |
| 日志 | 截断、丢弃、缺失来源、失败写入等未被当作成功忽略 |

不要要求每段正文都成为节点；要求的是业务问题所需内容在可检索片段中完整，并且关键范围关系能被定位。

原生技术状态不替代业务状态。批次建议记录为：待准备 → 已准备 → 核准通过 → 写入中 → 已落盘 → 读回通过 → 检索通过；任一阶段可停止为待修正/失败。它是本地运行记录，不是新平台审批功能。

## 13. 原生检索验收：本轮必须做到，但不改查询链路

### 13.1 固定被测查询条件

以原生 `mix` 作为主验收模式，固定查询模型、embedding、关键词提示、回答提示、Top-K、片段数、预算、重排状态和空历史。原生 `only_need_context`、`only_need_prompt` 可用于上下文检查；它们是1.5.7已有参数。[S5]

先保持原有查询配置建立对照。不得一边改变导入方式，一边给每道题加专用关键词或提高预算，再把收益全部归因于抽取改进。`naive` 可用作“仅向量片段”的诊断对照，不替代主验收。

测试问题是独立完整的中文问题，不需要平台改写。例如“某产品计划一有哪些保障责任”，而不是“它呢”。但还要覆盖只说产品、不指定计划的自然问法，不能人为补上正确计划来提高通过率。

### 13.2 三层判定，分别记录

| 层次 | 检查什么 | 失败归属 |
|---|---|---|
| 原生索引存在性 | 核准知识和证据是否真正进入图、向量、片段 | 导入/写入问题 |
| 原生实际上下文 | 本次检索、预算处理后是否包含完整支持依据 | 召回/预算问题，或导入单元组织不合理 |
| 最终答案 | 前提、范围、比例基数、例外和引用是否表达正确 | 证据齐全时主要是生成问题 |

最终答案正确但上下文缺少关键证据，不能算可靠通过，可能是模型碰巧知道或猜对。反过来，已经找到完整证据但答案错误，不应重新全量抽取。

### 13.3 同请求证据

仅检索验收时，`only_need_prompt` 返回的就是那一次检索准备的生成输入，可以独立判定该次检索是否完整。

测试最终答案时，需记录该次真正发给回答模型的输入。可使用只记录、不修改内容的模型调用追踪，保存提示摘要、实际文本、配置和请求编号。不需要改检索算法。

分别调用“查询数据”和“生成答案”是两次执行；前者不能自动代表后者实际看到的内容。没有同请求追踪时，报告只能称“独立检索试查”，不能声称已经证明某条答案的证据完整性。

### 13.4 测试输入与标准答案隔离

导入运行只能读取原件、身份清单和通用配置；问答运行只能读取问题和固定查询参数。预期结论、必需证据范围、禁止混用内容、评分标准放在独立评测目录，回答结束后才由评分器读取。

证据单元根据文档内容组织，不围绕标准答案生成FAQ。调试集与留出验证集分开，留出集不能参与提示词和片段逐题调优。

### 13.5 评价完整性时允许等价来源

同一事实可能在条款与说明书中各有完整支持，不应机械要求所有重复来源都出现。标准答案定义“最小充分证据组”，可以允许多个等价组；但每组都必须覆盖该题需要的对象、条件和例外。

对于计划对比、责任总览等多部分问题，需要分别覆盖各部分，不能只找到一个计划就记为全题命中。

### 13.6 本轮建议指标

| 指标 | 计算/检查口径 | 验收要求 |
|---|---|---|
| 资料盘点覆盖 | 纳入＋明确排除＋待核 = 全部输入资料 | 100%有状态，不静默漏件 |
| 原文定位一致 | 可用证据内容、位置与对应解析版本一致 | 程序检查100%通过；关键结构另核原件 |
| 核心结构覆盖 | 计划表、责任标题、关键限制/例外有处理落点 | 核心清单全部通过 |
| 图谱范围错误 | 已核关键事实的产品/计划/责任归属错误数 | 核心人工集为0 |
| 关键证据组完整召回 | 本次实际上下文含至少一个完整充分证据组 | 核心问题全部通过 |
| 一般信息召回 | 普通题可从实际上下文获得所需信息 | 首轮目标可设≥95%，不足需逐题记录 |
| 范围误用 | 答案错误使用其他产品、计划或责任规则 | 固定回归集为0 |
| 无依据强结论 | 缺证仍给确定产品结论 | 固定回归集为0 |
| 可答题拒答 | 原文有完整答案但系统说无依据 | 计为失败，不能用拒答提高安全分 |
| 重启一致性 | 新实例读同一落盘索引仍可通过关键题 | 必须通过 |

以上是建议验收目标，不是已达到的成绩。原生全库检索可能出现无关候选；“候选噪声”和“最终误用”分别记录，不能把名称前缀当成严格隔离承诺。

### 13.7 无法仅靠导入解决时如何结项

已经证明原文、抽取和索引正确，但在固定原生查询预算下仍持续缺少关键证据，报告应记录“原生召回/预算未通过”。本轮可以修正不合理的片段、命名或重复内容；不能自动扩大为在线范围过滤、在线补证或问答平台联调。

需要查询侧能力才能解决的事项进入独立待办，不隐瞒，也不把当前导入专项称为全面通过。

## 14. 真实资料案例：从原文到可检索信息

本节是设计演示和验收要求，不是已执行结果。示例依据固定仓库中的《京康优护医疗保险投保及核保规则.md》；正式业务标准还需核对原件与对应版本。[S7]

### 14.1 案例一：计划责任不能混用

该资料给出了计划一包含住院医疗和住院前后门急诊责任、计划二在此基础上增加住院津贴的对应关系。

| 步骤 | 本方案的处理 |
|---|---|
| 解析 | 识别“投保计划与保额”标题、计划列、保障责任列和两行对应 |
| 范围 | 形成两条明确映射；不把计划二新增的责任提升成产品通用责任 |
| 检索单元 | 小表整体保留，附产品、资料版本、表名及其相关说明 |
| 抽取 | 产品、计划一、计划二、真实责任；对应关系使用该表作为证据 |
| 关系表达 | 共性责任可以被两个计划有依据地关联，新增责任不自动复制到计划一 |
| 验收 | 分别问计划一、计划二、两者差异，以及只问产品保障责任 |

没有原文支持时，不从“计划二包含一项责任”反推“所有其他计划肯定不包含”；本例应依据完整计划对应材料回答，而不是依靠缺边推断否定。

### 14.2 案例二：比例必须带基数和触发条件

资料中有一项医疗结算方式条件，对应“约定比例的60%”这一表达。完整导入不能只提取数字60%。

一个合格检索单元至少要使模型能够读到：这是哪一产品和哪类责任、采用什么投保/就诊结算方式时适用，以及比例是以什么为基数。

| 不合格导入 | 合格方向 |
|---|---|
| 规则：赔付比例60% | 原文完整条件＋“约定比例的60%”＋责任范围 |
| 60%作为全产品的独立节点 | 保存在有范围的给付规则中 |
| 主句进入chunk，条件只在旁路检查表 | 条件与主句都进入实际原生chunk |

验收问题可以包含：该比例是否总是适用、它是约定比例还是实际给付比例、什么结算条件触发。要求答案保留原文的条件和基数，不自行设定金额演算。

### 14.3 案例三：同一免赔额不能推出所有规则共享

资料明示了住院前后门急诊与住院责任使用同一约定年免赔额。应抽取这项明确共用关系，而不能进一步生成两项责任在等待期、期满延续、次数或给付限制上全部相同的结论。

本例的验收重点不是“图连得更密”，而是只保留已经有依据的共性。涉及其他规则时另找对应条款；未提供依据就记录缺项，不从免赔额关系推导。

### 14.4 案例四：同名局部规则隔离（仅结构反例）

构造测试原文甲：“计划一的责任甲适用某条件”；原文乙：“计划二的责任乙适用另一条件”。两者都使用相同规则短名。这是工程测试材料，不是实际产品条款。

导入后应具有不同的规则身份和原文来源。改变导入顺序、重新启动后，不能出现后一条覆盖前一条，或两段被摘要成一个共同规则。

### 14.5 一条完整的阶段追踪示例

```text
原件/资料：产品资料中的计划对应表
    ↓ 结构块
“投保计划与保额”／表头／计划一行／计划二行／相关说明
    ↓ 证据目录
各原文区间分别编号，绑定同一资料版本
    ↓ 完整检索单元
产品身份＋完整计划表＋必要说明，来源标记与正文分开
    ↓ 核准实体关系
产品、计划、责任及表格直接支持的对应关系
    ↓ 原生写入
真实chunk＋片段向量＋范围明确的节点/边及其向量
    ↓ 读回
表格对应未变、没有补出其他责任、来源能定位
    ↓ 原生问答试查
“计划一有哪些责任？”和“不指定计划的保障问题”均检查实际上下文
```

整个过程中不把标准答案写进导入材料，也不新增产品专属判断分支。

## 17. 性能设计：把开销花在必要的导入工作上

### 17.1 导入阶段减少重复

一次解析结果按原件摘要和解析配置缓存；一次核准的完整单元按内容、范围、依赖和抽取配置指纹缓存。导入写入时回放核准结果，不重新随机抽取。

新增定义或修改计划表可能影响引用它的多个单元，应沿依赖关系使相关缓存失效；未变化且合同指纹相同的核准单元可以复用。不能只按文件名判断是否需要重跑。

先用低并发稳定核验，再在不增加失败、限流和来源错配的前提下提高并发。并发不同不应改变逻辑身份和来源合并结果。

### 17.2 不把“实体越多”当质量目标

优先抽取真正有检索价值的产品、计划、责任、局部规则和必要定义。减少通用数字节点、重复上下文事实、整份合同式描述和无依据的共现关系。

保留真实约定的完整性，不能为了速度压缩掉例外，也不能为了看起来“全”而把每个词都变成节点。

### 17.3 合并、embedding与缓存

embedding模型和维度固定；原生内容可能进行长度处理，需记录哪些条目发生截断。[S6] 高风险规则不能依赖截断后的索引尾部仍保留关键信息。先缩小规则单元和重复描述，再考虑预算。

新的核准结果必须形成新的配置/内容指纹。原生抽取缓存、导入侧核准缓存、查询答案缓存是三类不同缓存，不能只清理其中一类就认为新方案已生效。

### 17.4 性能报告

| 导入指标 | 查询指标 |
|---|---|
| 原件解析耗时、单元数量 | 检索耗时、首次答案耗时、总耗时 |
| 抽取调用数、补抽数、输入输出token | 实际生成上下文token |
| 合并调用数、是否发生模型概述 | 不同产品/计划的候选噪声 |
| 三类向量生成耗时 | 关键证据组完整召回率 |
| 读回检查耗时、失败/重试数 | 冷缓存/热缓存分别记录，P50/P95注明样本数 |

没有实测前不承诺固定秒数。准确性达到目标后，再比较相同问题集下的速度；不能靠删掉必要条件换来更快回答。

## 18. 更新与失败恢复：本轮采用最小安全策略

本轮优先在新候选工作区验证，不在已通过基线索引里反复增删重抽。多个产品仍放在同一候选库测试；不是每款产品永久一个库。

| 变更/失败 | 本轮处理 |
|---|---|
| 原件、表格或条款修改 | 重新解析受影响原件；沿依赖标记相关单元失效 |
| 提示、中文类型或命名策略修改 | 建新候选批次，不能只改配置后把旧图当新结果 |
| embedding模型/维度修改 | 独立候选重建对应向量，不混用两种空间 |
| 网络超时但结果未知 | 查询已有回执与原生状态，不立即重复写入 |
| 部分写入或落盘失败 | 保留候选和日志做诊断；不把它作为通过版本 |
| 仅修改标准答案评分 | 不改索引；重新评测并记录评分版本 |

可以复用离线解析和核准缓存减少模型成本，但不要手工拼接两份原生索引JSON。已有原型会拒绝重复使用某些目标/回执，这种保护不应为了方便重跑而直接删除。[S2]

生产级逐文档增量替换、无停顿切换和多用户并发导入，不是本轮验收门槛。若无法在现有接口保证原地更新一致性，使用新候选重建并记录未实现项。

## 19. 分阶段实施与验收关卡

### 阶段A：保留基线，确认问题到底丢在哪

选少量代表性产品，以京康优护的真实多计划资料作为重点。固定源文件、源码、模型和原生查询配置，保存失败问题的原文、现有索引和实际上下文。

交付：资料清单、缺件/排除项、固定基线报告。不要先全量重导几十款产品。

### 阶段B：只改输入组织，先证明原文可检索

完成结构解析、范围候选、完整检索单元和证据编号。保留原始文字，不用模型重写条款。先检查准备后的片段是否真的包含责任、计划及必要条件。

交付：原文—单元映射、片段预览、核心结构检查报告。关键计划表或范围仍不清时，不进入批量抽取。

### 阶段C：接入核准抽取和原生写入

完成中文类型、作用域身份、证据指针、覆盖检查、局部修复与核准结果回放，落盘后重新读回。优先验证同名不同范围、相同文字不同来源、复制上下文不重复造事实等工程反例。

交付：新候选索引、核准结果、来源映射、读回报告。不能把图存在、向量缺失或关键条件被摘要的候选记为通过。

### 阶段D：固定原生查询验证，然后扩大到混库

先在代表性产品上运行事实、计划、差异、定义、例外、总览类问题，再将多个产品放入同一候选库。增加未参与调试的问法和产品，检验不是只适配既有几道题。

交付：逐题真实上下文、最小充分证据组检查、原答和性能对照。核心问题有一项关键范围误用或关键证据缺失，仍记为未通过。

### 推荐初批题目结构

首轮可从40–60题起步，数量是工作安排建议，不是正确性证明。覆盖下面这些类别比凑数量更重要：

| 类别 | 必测内容 |
|---|---|
| 产品与责任 | 单责任事实、全部责任总览、可选责任前提 |
| 计划 | 指定计划、不指定计划、计划差异、相同责任跨计划 |
| 限制与例外 | 否定、比例基数、单次/年度/累计、时间起点与终止对象 |
| 结构 | 跨页表格、脚注、后置定义、明确跨文件资料关系 |
| 混库 | 同名规则不同产品、同产品不同版本、不同计划不会合并 |
| 缺失与错误前提 | 资料确实缺失、用户把局部规则说成通用规则 |
| 稳定性 | 重启、缓存、导入顺序变化后的核心问题 |

原文可答却拒答算失败；来源缺失但猜中了答案也算不可靠。缺少费用/时间等个案条件的题，只要求正确说明已知规则和缺项，不要求作承保或赔付决定。

## 21. 给开发执行的最终约束

本轮只在 LightRAG 仓库内开发导入链路；从真实产品资料生成能被原生检索直接读到的完整证据片段，以及有明确范围和来源的中文实体关系。

优先使用现有准备、证据抽取与SDK导入模块。产品、计划和责任来自原文及已核身份，不从标准答案或产品专属代码推导。复用原生存储，不另建完整事实问答系统。

准备与预检查通过后才写入新候选工作区；核准结果与实际原生chunk必须一致。落盘后用新实例和固定原生查询检查实际上下文，不增加在线补证来替导入“补考”。

失败时按“解析→完整单元→抽取→合并→向量/来源→原生召回→生成”定位，只修对应层。核心缺陷未解决就明确未通过，不用更多节点、更大Top-K、更强模型或更多拒答代替质量证明。

**最终交付不是一张更大的图，而是一批独立可验收的产品知识：关键资料找得到，适用范围不混淆，影响结论的原文依据找得全。**
